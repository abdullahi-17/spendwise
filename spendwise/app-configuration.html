How SpendWise is delivered, secured, tested, and operated. This page connects the AWS portfolio deployment to the production mobile backend design, with implementation status tied to observed evidence.

01 Cloud architecture

Cloud architecture

The engineering story has two boundaries: the browser demo and its AWS delivery configuration, and the production mobile platform design. The demo runs locally with matching browser and Python insight rules. API integration, alarms, budget notifications, and artifact rollback are prepared in code; their hosted results still need verification. React Native and Supabase remain a separate mobile design.

Cloud engineering demo

Application and API

The browser demo supports a complete sample reflection without AWS. An optional API Gateway endpoint calls a Python 3.12 Lambda function. The handler validates the three accepted answers; browser rules provide a fallback if the API is unavailable. No retailer cart, payment, reminder, or saved history is connected.

Delivery and operations

GitHub Actions checks the application and templates, then packages the tested website with a SHA-256 manifest. Deployment and rollback share a lock. CloudWatch alarms and an optional account-wide budget template are included; live release, alert delivery, and recovery demonstrations remain pending.

Planned production mobile platform

Supabase Auth and PostgreSQL provide the target account and private-history layer. The insight endpoint would validate the Supabase session before processing a request. That authentication is a production requirement: the current Lambda source does not implement it. Mobile distribution is separate from the static website deployment.

02 CI/CD and infrastructure as code

CI/CD and infrastructure as code

The repository workflow defines a test-gated website release. A successful local run verifies its tests; a successful GitHub Actions run is still required to verify the hosted pipeline.

Configuration kept in the repository

  • .github/workflows/deploy.yml: tests, artifact packaging, OIDC role assumption, S3 upload, cache invalidation, and public-byte verification.
  • .github/workflows/rollback.yml: restore a verified artifact from a successful main-branch release.
  • infrastructure/template.yaml: API Gateway, Python 3.12 Lambda, scoped logging, throttling, and operational alarms.
  • infrastructure/budget.yaml: optional account-wide monthly budget notifications.
  • infrastructure/github-oidc.yaml: reusable role/provider template; the live role was created separately.
  • infrastructure/cloudfront/spendwise-router.js: hostname-specific request rewriting.

The existing bucket, DNS records, certificate, and CloudFront distribution are not fully represented by these templates. Full infrastructure reproducibility would require managing or importing those resources deliberately, without replacing the shared portfolio infrastructure.

03 Security and isolation

Security and isolation

Deployment access

GitHub OIDC exchanges workflow identity for temporary AWS credentials. The role template trusts the SpendWise repository’s main branch. Its policy allows listing the SpendWise prefix and reading or uploading its objects, with no delete permission.

Shared-resource boundary

The repository role policy grants no CloudFront distribution-update permission. It can create invalidations on the shared distribution; the workflow refreshes /spendwise/* and viewer-facing /demo.html, /js/* and /css/* paths. The latter can evict cached assets for other hostnames sharing the distribution, but do not edit their origin objects. Invalidation paths are controlled by workflow code, not IAM. The role also needs GetInvalidation to wait for completion; apply the template update to the live role before release.

Production data controls

User-owned PostgreSQL tables need tested row-level security policies. The API must verify session tokens and record ownership. Privileged database credentials stay on the server. Mood answers, purchase details, and reflection text stay out of general analytics and diagnostic logs.

The mobile app should retain only necessary data, offer export and deletion, and keep shopping-app detection local where possible. Secure device storage and platform-specific permission handling belong to the mobile implementation, not the website hosting layer.

04 Application and data design

Application and data design

A small rules engine keeps the insight response explainable. Rules run from most specific to least specific, returning the first match and otherwise a default reflection. The browser fallback and Python rules must return the same wording for the same answers.

Production accounts and private history would need authenticated access and ownership checks. The demo calculates no psychological score.

05 Operations, cost and recovery

Operations, cost and recovery

Observability

The API template defines bounded log retention, stage throttling, and alarms for API server errors, latency, and Lambda throttles. An optional SNS email subscription needs confirmation. These alarm configurations have passed local template checks; live metric and notification evidence remains pending.

Cost control

Static delivery avoids an always-running web server. Review API traffic, data transfer, log retention, mobile build services, and database usage. Throttling reduces request rate; it is not a guaranteed spending cap. An optional budget template provides account-wide monthly actual and forecast notifications. Its threshold is configurable and it does not stop spending; live setup and delivery still need verification.

Recovery approach

Earlier deployment notes report S3 versioning; its current live state has not been rechecked in this audit. The rollback workflow restores website files from a verified successful main-branch artifact retained for 30 days, then refreshes the cache and compares public bytes. It leaves newer extra objects in place and does not restore infrastructure or the API. Uploads happen in place, so this is not an atomic release. A live rollback drill remains pending. Database backup restoration and compatible mobile/API releases need separate recovery procedures.

Before treating the platform as production-ready, demonstrate a complete release, a failed-test deployment block, restoration of a prior website version, and database recovery in a non-production environment.
